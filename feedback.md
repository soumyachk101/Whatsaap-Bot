## 1. `index.js`

---

**🟠 HIGH — No top-level error / unhandled-rejection handler**
`index.js` does not register a `process.on('unhandledRejection')` handler. If any unguarded `await` in a message handler or startup routine throws a rejection that no `try/catch` intercepts, the Node process will crash or (in Node ≥ 15) exit with a non-zero code. The bot will go offline until PM2 restarts it.

**Fix:** Add immediately after `import` statements:
```js
process.on('unhandledRejection', (err) => {
  console.error('[FATAL] Unhandled rejection:', err);
  // optional: log to telegram, exit cleanly so PM2 restarts
});
```
---

**🟡 MEDIUM — `bot.on('connection.update', ...)` fires before socket is ready**
The `connection.update` listener calls `onConnect` which does heavy setup. If the socket connection drops and reconnects, `onConnect` is re-entered. If `onConnect` has any state that is not idempotent (e.g. pushing onto arrays without clearing them, re-registering event listeners, re-initialising caches that should be fresh), the bot will accumulate stale state on each reconnect.

**Fix:** Verify `onConnect` is idempotent. Add a guard:
```js
let isConnecting = false;
async function onConnect() {
  if (isConnecting) return;
  isConnecting = true;
  try { /* setup */ } finally { isConnecting = false; }
}
```
---

**🔵 INFO — `bot.on('message', ...)` handler is async with no rate-limit on error logs**
The `message` handler is async and its internal errors are caught and logged, but on a busy group the error log volume can flood `console`. Consider adding a per-phoneId rate limit on error log frequency.

## 2. `connection.js`

---

**🟠 HIGH — Socket reconnection: no backoff / retry on `disconnected` state**
`connection.js` calls `connect()` on startup. If `connect()` fails once (network blip, Baileys WS error on first attempt), there is no automatic retry loop. The bot will sit disconnected until a manual restart.

**Fix:** Wrap the initial call in a retry loop:
```js
async function startWithRetry() {
  let attempt = 0;
  while (true) {
    try {
      await connect();
      return;
    } catch (err) {
      attempt++;
      const delay = Math.min(1000 * 2 ** attempt, 30000);
      console.error(`[connection] connect() failed (attempt ${attempt}), retry in ${delay}ms:`, err);
      await new Promise(r => setTimeout(r, delay));
    }
  }
}
```
---

**🟡 MEDIUM — `disconnect` event listener not guarded against double-fire**
`connection.on('disconnected', ...)` will fire on both intentional and accidental disconnects. If cleanup logic (closing HTTP server, flushing DB WAL, etc.) runs without an idempotency check, a double disconnect event could corrupt state or leave the WAL file open.

**Fix:** Add a `let isCleaningUp = false` flag; on first `disconnected` event, set it and run cleanup; on subsequent events, skip.

---

**🔵 INFO — `connection.on('close', ...)` and `disconnected` both may fire**
Depending on the Baileys socket implementation, both `close` and `disconnected` can fire. Make sure neither triggers a second `connect()` call (which would create a second socket and leak the first).

## 3. `sqlite.js`

---

**🔴 CRITICAL — WAL checkpoint / sync issue: `db.pragma('journal_mode = WAL')` called on every connection**
`sqlite.js` (673 lines) appears to open the database per query or per operation. If `PRAGMA journal_mode=WAL` is executed on every open, SQLite will return `WAL` (unchanged) — that's fine — but if the file handle is not properly closed between opens, SQLite will accumulate WAL file segments. On a long-running production process this causes `database.db-wal` to grow unboundedly and can trigger `SQLITE_FULL` errors under disk pressure.

**Fix:** Ensure `db.pragma('journal_mode = WAL')` is called once on module load (first open), not on every subsequent open. Add a module-level flag:
```js
let walEnabled = false;
function getDb() {
  // ...
  if (!walEnabled) {
    db.pragma('journal_mode = WAL');
    db.pragma('synchronous = NORMAL');
    walEnabled = true;
  }
}
```
---

**🟠 HIGH — No `db.close()` on process exit**
There is no `process.on('SIGINT')` / `process.on('SIGTERM')` handler that calls `db.close()`. If the process is killed or PM2 sends SIGTERM, the WAL file may not be checkpointed to `database.db`, causing data loss or corruption on next startup (SQLite will recover, but uncommitted transactions in the WAL are lost).

**Fix:**
```js
let dbInstance = null;
function closeDb() {
  if (dbInstance) {
    dbInstance.pragma('wal_checkpoint(TRUNCATE)');
    dbInstance.close();
    dbInstance = null;
  }
}
process.on('SIGINT', closeDb);
process.on('SIGTERM', closeDb);
```
---

**🟡 MEDIUM — No busy timeout: concurrent writes will throw `SQLITE_BUSY`**
If two async operations call `sqlite.js` functions concurrently (e.g. a message event and a cron job both write to the same table), the second write will get `SQLITE_BUSY` immediately (default busy timeout is 0 ms). This will surface as an unhandled error in whatever code called it.

**Fix:** Add a busy timeout on open:
```js
db.pragma('busy_timeout = 5000'); // 5 second timeout before SQLITE_BUSY
```
---

**🟡 MEDIUM — Prepared statement caching: verify no leak**
If `sqlite.js` caches prepared statements in a Map but never invalidates them when the underlying schema changes (via `dbControl` or migrations), old statements will throw `SQLITE_ERROR` on use.

**Fix:** Add a `cacheVersion` counter; bump it on any DDL statement; evict all cached statements when version changes.

## 4. `sessionStore.js`

---

**🟡 MEDIUM — No TTL on session store entries**
`sessionStore.js` (86 lines) stores keyed data (likely per-phoneId session tokens, cooldowns, or rate-limit counters). If entries are never expired, the in-memory store will grow unbounded over weeks of uptime. For a production bot with many group sessions, this is a slow leak.

**Fix:** Add a TTL sweep:
```js
setInterval(() => {
  const now = Date.now();
  for (const [key, val] of store.entries()) {
    if (val.expires && val.expires < now) store.delete(key);
  }
}, 300_000); // sweep every 5 min
```
---

**🔵 INFO — Race condition on read-modify-write**
If two concurrent async operations both call `store.get(key)`, modify, and `store.set(key, ...)` without holding a lock, one update will be lost. For fields like `messageCount` or `lastSeen`, this is acceptable (at-most-once update). For anything critical, use a queue or a `Promise`-based lock.

```js
const logger = pino({

  ]

// pass `logger` in makeWASocket options
```

If `markOnline` / `online` event handling is not present, the bot's presence state in WhatsApp will remain `last` instead of `online`. This is cosmetic but affects user trust (contacts see the bot as "last seen" rather than "online").

**Fix:** Add in the `open` handler:
```js
connection.on('open', () => {

```

**🔵 INFO — `getSocket.js` uses `useSQLiteAuthState` (a local Baileys-compatible auth store)**

## 6. `functions/getMessagesEvent.js`

---

**🔴 CRITICAL — `msg.key.fromMe` check: self-sent messages can bypass rate limiter**
`getMessagesEvent.js` processes all incoming messages. The standard guard is:
```js
if (msg.key?.fromMe) return;
```
However, if a user sends a message from the bot's own number (unlikely) or if the `fromMe` flag is not set on some Baileys message types (broadcasts, status updates), those messages will be processed. More critically: if the `fromMe` check happens AFTER the rate limiter call, self-messages could consume the rate limit budget for the phoneId, starving legitimate user messages.

**Fix:** Move `fromMe` check to the very first line of the handler, before any rate-limiter or queue calls:
```js
export default async function getMessagesEvent(msg) {
  if (msg.key?.fromMe) return; // ← FIRST, before anything else
  // ... rate limiter, queue, etc.
}
```
---

**🟠 HIGH — Message queue: no `unshift` / drain on socket reconnect**
If `messageQueue.js` (imported here) enqueues messages during a brief disconnect, and the socket reconnects, the queue must be drained in order. If the drain happens via a `while(queue.length > 0) shift()` loop without awaiting each `process()`, messages can arrive out of order or be dropped if the handler throws mid-drain.

**Fix:**
```js
async function drainQueue() {
  while (queue.length > 0) {
    const item = queue.shift();
    try { await processMessage(item); }
    catch (err) { console.error('Drain failed:', err); /* re-queue or skip */ }
  }
}
```
---

**🟡 MEDIUM — `msg.sessionId` derived lookup without fallback**
If `msg.sessionId` is `null` (which Baileys sets for some message types), the code likely does `sessions.get(msg.sessionId)` which returns `undefined`, and the subsequent `session.foo` access will throw `TypeError: Cannot read property 'foo' of undefined`.

**Fix:**
```js
const session = sessions.get(msg.sessionId);
if (!session) { console.warn('No session for msg', msg.key?.id); return; }
```
---

**🟡 MEDIUM — `quoted` message parsing: no schema validation on `msg.quoted`**
Baileys' `quoted` message object shape changes between versions. If a `quoted` message is received that has `contextInfo.quotedMessage` but no `contextInfo.participant`, the JID formatting will produce `undefined` and the lookup will silently fail or throw.

**Fix:** Wrap the quoted-message extraction in a try/catch and a shape guard:
```js
let quoted = null;
try {
  if (msg.message?.extendedTextMessage?.contextInfo?.quotedMessage) {
    quoted = msg.message.extendedTextMessage.contextInfo.quotedMessage;
  }
} catch { /* ignore */ }
```

## 15. `functions/downloadQueue.js`

---

**🟠 HIGH — No maximum queue size: unbounded memory**
If a large burst of media download requests comes in (e.g. a group of 500 users all request media at once), `downloadQueue` will enqueue all of them. Each queued item holds a reference to the message data + response buffer. Under load, this can exhaust Node's 512MB heap (`--max-old-space-size=512`).

**Fix:** Add a `MAX_QUEUE_SIZE` constant (e.g. 100):
```js
if (queue.length >= MAX_QUEUE_SIZE) {
  // reject new requests immediately, tell user to try later
  return { ok: false, error: 'Download queue is full, please try again in a minute.' };
}
```
---

**🟡 MEDIUM — No backpressure: workers process at full speed regardless of disk I/O**
The download workers don't await disk writes before grabbing the next item. If the disk is slow (which EC2 `gp2` volumes are under heavy random I/O), the in-memory buffer will grow because each worker holds the file data in RAM until `fs.promises.writeFile` completes, and the next item is grabbed immediately.

**Fix:** Use a worker-pool pattern with `await fs.promises.writeFile` BEFORE pulling the next item from the queue:
```js
while (true) {
  const item = queue.shift();
  if (!item) break;
  const buffer = await downloadMedia(item);
  await fs.promises.writeFile(item.path, buffer); // ← await before next item
}
```
---

**🟡 MEDIUM — File cleanup: no TTL on `temp/` media files**
Downloaded media is written to `temp/` (per `package.json` `directories` config). If files are not cleaned up after they are sent, `temp/` will grow without bound. On a production EC2 instance with 8GB RAM and limited disk, this will fill the volume.

**Fix:** Add a cleanup cron:
```js
setInterval(() => {
  const cutoff = Date.now() - 3600_000; // 1 hour
  fs.readdir('temp', async (err, files) => {
    for (const file of files) {
      const stat = await fs.promises.stat(`temp/${file}`);
      if (stat.mtimeMs < cutoff) await fs.promises.unlink(`temp/${file}`);
    }
  });
}, 3600_000); // hourly
```

## 23. `functions/rateLimiter.js`

**🟠 HIGH — No persistence: rate limits reset on every bot restart**
If `rateLimiter` is in-memory (a `Map` of phoneId → timestamps), every time PM2 restarts the bot, the entire rate-limit state is wiped.
